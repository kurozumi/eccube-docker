# 負荷試験（何 PV/秒まで耐えるかを測る）

`bin/loadtest.sh` で、フロントに「毎秒何 PV」の負荷をかけます。**何台・どの大きさのサーバーが
要るか、どこを先に強くするか**は、測ってから決めます。[大規模アクセス](scale.md) のどの段階に
進むかも、ここで出た数字で決めます。

```bash
bin/loadtest.sh smoke                  # 動くかだけ（1 PV/秒・30 秒）。最初に必ずこれ
bin/loadtest.sh stress --rate=100      # 25〜150 PV/秒へ段階的に。どこで崩れるかを見る
bin/loadtest.sh load   --rate=80       # 想定の山 80 PV/秒を 5 分保つ
bin/loadtest.sh spike  --rate=80       # 平常（10%）から 10 秒で山へ（セールの開始・メルマガの直後）
```

中身は k6（公式の Docker イメージ。手元に何も入れなくてよい）で、シナリオは `docker/k6/eccube.js`。
結果は `var/loadtest/<日時>-<流し方>/` に残ります。

## どこに流すか

**本番には流さない。** 自分で自分のサイトを落とすことになります（お客さんが入れない）。
Cloudflare などの前段が攻撃と見て止めることもあります。

流すのは、**本番と同じ形の検証環境**です。

| 揃えるもの | なぜ |
|---|---|
| サーバーの大きさ（CPU・メモリ）と台数 | 数字はサーバーの大きさでそのまま変わる |
| `.env`（`PHP_FPM_*`・`COMPOSE_PROFILES`・`APP_ENV=prod`）と `docker/mariadb/conf.d` | php-fpm の枠と Redis の有無で、詰まる場所が変わる |
| **プラグイン** | 1 ページで流れる SQL の数はプラグインで大きく変わる。いちばん効くことが多い |
| **データの量**（商品・カテゴリ・会員・受注） | 商品が 2 件と 2 万件では、一覧と検索の重さが桁で違う |

**k6 はサーバーとは別のマシンから流す。** 同じマシンで流すと、k6 自身（遅くなると数百〜千人分の仮想ユーザー）が
サーバーと CPU を取り合い、サーバーの限界が実際より低く出ます。手元の Mac で手元のスタックに流すのは、
シナリオが動くかと、大まかな形（どこが先に詰まるか）を見るためだけにしてください。

本番のデータを持ち込むなら `bin/backup.sh` → 検証環境で `bin/restore.sh`（[バックアップ](backup.md)）。
**戻す前に、メールを送れないようにする。** 会員の本物のアドレスが入っていて、Messenger の待ち行列に
送る前のメールが残っていれば、戻した瞬間に worker が送り始めます。`.env` を書き換えただけでは、
動いているコンテナには効きません。この順番で:

```bash
docker compose stop worker                                  # 1. 送る係を止める
# 2. .env の MAILER_DSN=null://null にする
docker compose up -d --force-recreate ec-cube               # 3. 新しい値でコンテナを作り直す
docker compose exec ec-cube printenv MAILER_DSN             # 4. null://null と出ることを確かめる
# messenger を使っているとき（COMPOSE_PROFILES に messenger）だけ、worker も作り直して確かめる。
# 使っていないのに worker を名指しすると、profile を無視して要らない worker が立つ
docker compose up -d --force-recreate worker
docker compose exec worker printenv MAILER_DSN
bin/restore.sh backups/<日時>                                # 5. ここで初めて戻す
```

SMTP の値が残った worker を動かしたままにしないこと。DB には個人情報が入っているので、検証環境も本番と同じだけ守ってください。

`bin/loadtest.sh` は、相手が手元（127.0.0.1 / localhost）でないときは、相手のホスト名を打たないと流しません
（非対話なら `CONFIRM_LOADTEST=<ホスト名>`）。手元でも、相手がこのプロジェクトの nginx のポートで
なければ止めます（別名で立てた別のスタックへ流さないように）。

## 目標の決め方

月間の PV から、山の PV/秒を出します。

```
山の PV/秒 ≒ 月間 PV ÷ 30 ÷ 86,400 × 山の倍率
```

山の倍率は、EC では **5〜10**（夜とセール・メルマガの直後に集まる）。アクセス解析に「1 分ごとの最大」が
あれば、そちらを使ってください。

| 月間 PV | 平均 | 山（×5） | 山（×10） |
|---|---|---|---|
| 300 万 | 1.2 PV/秒 | 6 | 12 |
| 3,000 万 | 12 PV/秒 | 58 | 116 |
| 3 億 | 116 PV/秒 | 579 | 1,157 |

**「アクセス」がリクエスト数（画像・CSS・JS を含む）なら、PV はその 1/5〜1/10 です。** このシナリオは
PHP を通るページだけを流します（静的ファイルは CDN や nginx の長期キャッシュが返すもので、混ぜると
PHP と DB の限界がぼやける）。

## 流す順番

1. **smoke** … シナリオがそのサイトで動くか。失敗が 0 で、カートに入ることを確かめる
2. **stress**（`--rate=` は目標の山くらい）… 25% 刻みで 150% まで上げる。**どの段で崩れ始めるか**を見る
3. 直す（下の「詰まった場所ごとの打ち手」）→ もう一度 stress。数字が上がったかを比べる
4. **load**（`--rate=` は目標の山）… 山を保てるか。数分たってから崩れるもの（DB の接続・メモリ・セッションの増え方）を見る
5. **spike** … 急に来たときに、立ち上がりで落ちないか

1 回の stress はおよそ 15 分です。条件（`conditions.txt`）が残るので、何を変えたら何が変わったかを並べて比べられます。

## 流れるもの

1 回の繰り返しが 1 ページです。比率は一般的な EC の閲覧の内訳に寄せた目安なので、アクセス解析の
実数があれば `docker/k6/eccube.js` の `MIX` を合わせてください。

| ページ | 比率 | 中身 |
|---|---|---|
| トップ | 15% | `/` |
| 商品一覧 | 20% | `/products/list`（1〜2 ページ目） |
| カテゴリ | 20% | `/products/list?category_id=…`（トップのリンクから集めたもの） |
| 検索 | 10% | `/products/list?name=…`（当たる語と当たらない語） |
| 商品詳細 | 35% | `/products/detail/…`（一覧から集めた商品） |

これとは別に、閲覧の `--cart-ratio`（既定 0.1）の割合で「商品詳細 → カートに入れる → カート画面」を流します
（1 回で 3 PV）。規格のある商品は、在庫のある組み合わせを選びます。

**流さないもの**: 注文（本物の受注・在庫の引き当て・メールが作られる）、ログイン、会員登録、管理画面、静的ファイル。
カートに入れる流れは、DB にカートの行（`dtb_cart`）とセッションを作ります。**毎回が新しい訪問者**として
流れる（k6 は繰り返しごとに cookie を捨てる）ので、セッションは PV の数だけ増えます。

到着数を固定する流し方（k6 の `ramping-arrival-rate`）です。サーバーが遅くなっても、送る数は減りません。
人数（VU）を固定して流すと、遅くなるほど送る数も減り、限界の手前で「まだ余裕がある」ように見えてしまいます。

## 読み方

```
== 負荷試験の結果（stress、山 60 PV/秒、cart 0.1）==
リクエスト   …
失敗の割合   0.00%
取りこぼし   0 回
ページごとの応答時間        中央値     p95      p99      最大
  detail …
コンテナごとの CPU の最大（100% = 1 コア）:
  …-ec-cube-1   …
  …-db-1        …
php-fpm: 子プロセスが上限（max_children）に達した記録が … 件
```

| 見るところ | 意味 |
|---|---|
| **失敗の割合** | 5xx・タイムアウト。1% を超えたら不合格。502 / 504 は php-fpm が受けきれていない |
| **取りこぼし** | 送るはずだった繰り返しを、待っている人（VU）が足りず送れなかった数。**多ければ、サーバーが追いついていない**（応答が遅すぎて人が溜まった） |
| **p95** | 95% のページがこれより速い。既定の合格の線は 1 秒（`--p95=`） |
| **ec-cube の CPU** | 「100% = 1 コア」。割り当てたコア数 × 100% に張り付いていれば、PHP の計算が先に詰まっている |
| **db の CPU** | 高いのに ec-cube に余裕があるなら、DB が先 |
| **max_children** | php-fpm の子プロセスが足りなかった。CPU に余裕があるのにこれが出ていれば、枠が狭い |

崩れ始めた段（p95 が急に伸びる・取りこぼしが出る）の **1 つ前の段**が、その構成で安心して受けられる量です。
目標の山がそれを超えるなら、下のどれかで強くします。

`summary.json` に全部の数字が、`docker-stats.csv` に 5 秒ごとのコンテナの CPU / メモリがあります（手元に流したときだけ）。
別のマシンから流すときは、サーバーの側で `docker stats` を開いておくか、監視（[監視](monitoring.md)）のグラフを見てください。
php-fpm の上限は、サーバーで `docker compose logs ec-cube | grep max_children` で見られます。

## 詰まった場所ごとの打ち手

| 詰まった場所 | 打ち手 | 文書 |
|---|---|---|
| php-fpm の枠（max_children） | `PHP_FPM_MAX_CHILDREN` を上げる（1 本 80MB ほど。メモリの範囲で） | [scale](scale.md)「単一ホスト強化」 |
| ec-cube の CPU | 1 台を大きくする → `--scale` で 1 台の中に増やす → ホストを並べる | [scale](scale.md)「水平スケール」「複数ホスト + LB」 |
| DB の CPU | 遅い SQL を見る（`docker/mariadb/conf.d` の `slow_query_log = 1`）→ Redis のキャッシュ（`COMPOSE_PROFILES=redis`）→ マネージド DB を大きく | [scale](scale.md)「単一ホスト強化」「DB を外に出す」 |
| 特定のページだけ遅い | そのページで動くプラグインを疑う。プラグインを外した検証環境で同じ stress を流して比べる | |
| 失敗が 502 / 504 | php-fpm の枠か、nginx の `fastcgi_read_timeout` より遅いページ | |

DB の読み取りを複製へ振り分ける仕組みと、ページのキャッシュは入れていません。EC-CUBE の作りで、設定だけでは
効かないか、ほかの人のページを配ってしまうためです（[scale](scale.md)「3. DB が詰まったら」）。

## 手元の参考値

**本番の見積もりには使えない数字です**（形を見るためのもの）。配布元が作ったときに、macOS の Docker
（8 CPU・8GB。k6 も同じマシン）で、配布イメージ `ec-cube:4.3`・サンプルデータ（商品 2 件）・プラグイン無し・
Redis 無し・`PHP_FPM_MAX_CHILDREN=20` のスタックへ `stress --rate=40` を流した結果（2026-11-20）:

```
  目標 PV/秒   実際 件/秒    中央値      p95     失敗
         10        11.7      87ms    506ms     0.0%
         20        24.7      69ms    215ms     0.0%
         30        37.6     135ms   1178ms     0.0%   ← ここで p95 が 1 秒を超えた
         40        49.2    1345ms   3974ms     0.0%
         50        58.1    8635ms  11158ms     0.0%
         60        65.2   18675ms  23558ms     0.0%
ec-cube の CPU 最大 997% / db 150% / max_children に達した記録 5 件
```

- 安心して受けられたのは 20 PV/秒（カートを含めて 25 件/秒）まで
- **先に詰まったのは PHP の計算**（ec-cube の CPU が全コアに張り付き、DB には余裕があった）。php-fpm の枠も上限に達した
- 失敗（5xx）は最後まで 0。崩れ方は「エラー」ではなく「待たされる」で、p95 が 20 秒を超えても 200 を返し続けた。
  **お客さんから見ると、落ちる前にまず遅くなる**
- 最初の段の p95 が 2 段目より遅いのは、OPcache と Doctrine のキャッシュが温まる前のリクエストが入るため

## 終わったら

- カートの行（`dtb_cart`）が流した分だけ増えています。検証環境なら DB ごと捨てるか、`bin/reset.sh` で初期化してください（**本番構成の環境では使わない**。[データの安全](data-safety.md)）
- セッションも流した PV の数だけ増えます（ファイルなら `var/sessions`、Redis なら期限切れで消える）
- `var/loadtest/` は git にも backup にも入りません。要らなくなったら消してかまいません
