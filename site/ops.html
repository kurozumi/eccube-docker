更新と反映

パッチはその日のうちに当て、本番にはレビュー済みのものしか出さない。そのための置き場所の分け方と、3 枚の壁です。

パッチはその日のうちに

EC-CUBE のパッチ（4.3.1 → 4.3.2 など）は、やることが 2 つだけ。プラグインの移植が要るのはメジャー・マイナー（4.3 → 4.4）だけです。

1

環境（eccube-docker）を新しくする

bin/self-update.sh

コマンド・compose・スクリプトが新しいリリースに揃う。差分は git で見えるので、何が変わるか分かってから進める。

2

EC-CUBE を上げる

bin/upgrade.sh ~4.3.0 --prod

退避 → 新しい EC-CUBE でプラグインが動くかを、お店に触る前に確認 → メンテナンス表示 → migration → 疎通。危ないものを見つけたら、お店に触る前に止まる。

速い理由は 1 つ。あなたが直したものと EC-CUBE が、別々に更新される

EC-CUBE の中身を直接編集した環境は、上げるたびに「どこを直したか」の調査から始まります。ここでは置き場所が最初から分かれています。

あなたのもの — git で持つ

  • カスタマイズした PHP（app/Customize/）
  • 直したテンプレート・テーマ（app/template/）
  • 独自の CSS / JS（html/user_data/）
  • プラグイン、migration、設定（app/Plugin/ ほか）

パッチを当てても1 ファイルも触られない。上書きされる心配がないので、当てる前に「どこを直したか」を思い出す必要がない。

EC-CUBE と PHP — イメージで入れ替える

  • EC-CUBE と、それが使うライブラリ（vendor）
  • PHP、拡張、php-fpm、nginx

手で編集しないので、PHP は新しいイメージを引き直すだけ（bin/deploy.sh）、EC-CUBE は bin/upgrade.sh が入れ替える（イメージを引くだけでは、動いている EC-CUBE は古いまま）。だからパッチが出たその日に当てられる。EC-CUBE を直接編集した環境ではこれができない。

丸ごと写さない、が守られる テンプレートは「直すファイルだけ」を置く決まり。丸ごと写すと、上げたときに古いほうが勝ち続けて直したはずの不具合が戻ります。bin/theme.sh diff と bin/plugin.sh template diff が、EC-CUBE 側で変わったファイルを上げたあとに挙げます。

バージョンを変えるのは、それぞれ 1 コマンド

PHP・EC-CUBE・この環境（eccube-docker）は、別々に上げ下げできます。どれもデータ（受注・会員・商品・画像）はそのままです。

変えたいものやることかかる時間
PHP
8.2 → 8.3 など		 .env のタグの php8.2 を php8.3 に書き換えて
docker compose pull ec-cube && docker compose up -d		 約 20 秒
戻すのも同じ
EC-CUBE
4.3.1 → 4.3.2 など		 bin/upgrade.sh ~4.3.0 --prod 数分
失敗したら何も変えずに止まる
eccube-docker
v1.0.18 → v1.0.19 など		 bin/self-update.sh 1 分
差分を git で見てから commit
PHP だけ変えても EC-CUBE はそのまま PHP はイメージの中に、EC-CUBE と vendor はボリュームの中にあります。だからイメージを差し替えても入れ替わるのは PHP だけで、店のデータにも EC-CUBE の版にも触りません（作り直されるのはアプリのコンテナ 1 つ、約 20 秒）。合わない組み合わせのタグは存在しないので、壊れる前に pull が失敗します。選べる PHP は対応する EC-CUBEの表のとおりです。

本番には、レビュー済みの main しか出ない

エンジニアが直し、担当者が承認して、本番へ出す。「エンジニアが勝手に出す」と「担当者がうっかり出す」を、別々の壁で止めます。どれか 1 枚が無くても残りは効く。

①

GitHub — 承認が無いと main に入らない

bin/setup.sh protect

PR 必須、担当者（CODEOWNERS）の承認必須、force push と削除の禁止。管理者も例外なし。非公開リポジトリは GitHub の有料プランが要ります（無ければ②③だけで運用）。

②

手元 — main の先頭と同じものしか送れない

bin/deploy.sh --remote=shop:/srv/myshop
  ✗ いまのブランチは feature です。出せるのは main だけ

別のブランチ、コミットしていない変更、push していないコミット。どれか 1 つでも本番へは送らない。何もしなくて効きます。

③

サーバー — 見せて、打たせて、記録する

  コード: 3f2a1c0 → 9b7e4d2（3 コミット）
  ⚠ migration が含まれます
  続けるなら、プロジェクト名 myshop を入力:

y では通しません。指が覚えて通してしまわないように、プロジェクト名を打つ。誰が・いつ・何を出したかは var/deploy.log に残る。

正直に 本番の SSH を持つ人は②③を素通りできます。壁は「うっかり」を止めるもので「故意」は止められない。だから本番の SSH はエンジニアに渡さない、と決めてください。詳しくは 本番デプロイ。
