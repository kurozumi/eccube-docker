eccube-docker · __TAG__

EC-CUBE 4 を、手元でも本番でも
同じ構成で動かす。

本体はイメージに焼き、あなたのコードだけを git で持つ。直して、push して、 1 コマンドで反映する。データベースの更新もキャッシュも、メンテナンス表示の出し入れも、 そのコマンドの中に入っている。

はじめての人のための手引き GitHub Apache-2.0 · EC-CUBE 4.2 / 4.3 / 4.4

毎日やることは 3 つ

直す場所（手元）と動かす場所（サーバー）を分ける。それだけがこの環境の全部です。

1

手元で直す

bin/init.sh                # 初回だけ。http://localhost:8080/ で動く
bin/plugin.sh reload       # 反映されないとき
2

控えを送る

git add -A && git commit -m "何を直したか" && git push
3

サーバーに反映する

bin/deploy.sh --remote=shop:/srv/myshop

退避 → メンテナンス表示 → 取り込み → データベース更新 → キャッシュ → 確認 → 解除。 失敗したらメンテナンス表示のまま止まり、壊れた画面は出しません。

何が入っているか

EC-CUBE を本番で回して踏んだ穴を、コマンドと文書に落としてあります。

本体は触らない

EC-CUBE 本体はイメージに焼き込み、app/ と html/user_data だけを bind mount する。本体を上げても自分のコードは残る。

困ったら 1 コマンド

bin/plugin.sh doctor が、残骸の掃除・無効プラグインの検出・キャッシュの組み立て直し・疎通確認までやり、何が悪いかを日本語で出す。

引っ越しは 3 手順

bin/backup.sh が DB・画像・管理画面が書いたファイルを 4 点セットで退避。新しいサーバーでは clone → init → restore。

本体のバージョンアップ

bin/upgrade.sh がバックアップ・事前確認・スキーマ更新を順に。プラグインが新版で読めなければ、稼働中の環境に触る前に止まる。

環境そのものも更新できる

bin/self-update.sh が新しいリリースを取り込む。あなたのコードと .env には触らず、衝突すれば止まる。

Redis も Messenger も、要るときだけ

初回は無効。.env の COMPOSE_PROFILES に足すと、サービスの起動と設定の投入が同じスイッチで決まる。

始め方

git clone しません。 リリースの中身をもらって、自分専用の非公開リポジトリとして始めます。

# 配布元の最新リリースの中身をもらう（git の履歴は付いてこない）
curl -fsSL https://github.com/kurozumi/eccube-docker/archive/refs/tags/__TAG__.tar.gz | tar -xz
mv eccube-docker-__VER__ myshop && cd myshop

# 自分のリポジトリとして始める
git init -b main && git add -A && git commit -m "eccube-docker __TAG__ から開始"
gh repo create myshop --private --source=. --push

# 動かす
bin/init.sh
なぜ clone しないか clone だと origin が配布元のままで、あなたのコードを保存する場所が無い。fork は公開リポジトリだと非公開にできない。中身だけもらって自分のリポジトリにするのが、いちばん素直です。

対応する EC-CUBE

配布イメージを使うと、手元でビルドせずに数十秒で立ち上がります。.env に 1 行書くだけ。

系列イメージ備考
4.3ghcr.io/kurozumi/eccube-docker/ec-cube:4.3-__TAG__推奨
4.2ghcr.io/kurozumi/eccube-docker/ec-cube:4.2-__TAG__
4.4ghcr.io/kurozumi/eccube-docker/ec-cube:4.4-__TAG__上流の開発ブランチから焼いている。本番なら 4.4-<sha> で固定
 
# .env
ECCUBE_IMAGE=ghcr.io/kurozumi/eccube-docker/ec-cube:4.3-__TAG__
