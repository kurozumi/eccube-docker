eccube-docker · __TAG__ · Apache-2.0

EC-CUBE 4 のセキュリティパッチを、出たその日に当てる。
EC-CUBE も PHP も、1 コマンドで。

脆弱性の告知が来ても、当てるのが怖くて何か月も放置される。原因は「上げると壊れるかもしれない」 「戻し方が分からない」の 2 つです。ここでは EC-CUBE をイメージに焼き、あなたのコードだけを git で 持つ。だから上げるのはイメージを引き直すだけで、退避してから確かめ、 ダメなら何も変えずに止まる。インストールもサーバー移転も同じ考え方で 1 コマンドにしました。

やりたいことから選ぶ はじめての人のための手引き GitHub お問い合わせ / Issue

パッチはその日のうちに

EC-CUBE のパッチ（4.3.1 → 4.3.2 など）は、やることが 2 つだけ。プラグインの移植が要るのはメジャー・マイナー（4.3 → 4.4）だけです。

1

環境（eccube-docker）を新しくする

bin/self-update.sh

コマンド・compose・スクリプトが新しいリリースに揃う。差分は git で見えるので、何が変わるか分かってから進める。

2

EC-CUBE を上げる

bin/upgrade.sh ~4.3.0 --prod

退避 → 新しい EC-CUBE でプラグインが動くかを、お店に触る前に確認 → メンテナンス表示 → migration → 疎通。途中で失敗したら何も変えずに止まる。

速い理由は 1 つ。あなたが直したものと EC-CUBE が、別々に更新される

EC-CUBE の中身を直接編集した環境は、上げるたびに「どこを直したか」の調査から始まります。ここでは置き場所が最初から分かれています。

あなたのもの — git で持つ

  • カスタマイズした PHP（app/Customize/）
  • 直したテンプレート・テーマ（app/template/）
  • 独自の CSS / JS（html/user_data/）
  • プラグイン、migration、設定（app/Plugin/ ほか）

パッチを当てても1 ファイルも触られない。上書きされる心配がないので、当てる前に「どこを直したか」を思い出す必要がない。

EC-CUBE と PHP — イメージで入れ替える

  • EC-CUBE と、それが使うライブラリ（vendor）
  • PHP、拡張、php-fpm、nginx

手で編集しないので、新しいイメージを引き直すだけで新しくなる。だからパッチが出たその日に当てられる。EC-CUBE を直接編集した環境ではこれができない。

丸ごと写さない、が守られる テンプレートは「直すファイルだけ」を置く決まり。丸ごと写すと、上げたときに古いほうが勝ち続けて直したはずの不具合が戻ります。bin/theme.sh diff と bin/plugin.sh template diff が、EC-CUBE 側で変わったファイルを上げたあとに挙げます。

バージョンを変えるのは、それぞれ 1 コマンド

PHP・EC-CUBE・この環境（eccube-docker）は、別々に上げ下げできます。どれもデータ（受注・会員・商品・画像）はそのままです。

変えたいものやることかかる時間
PHP
8.2 → 8.3 など		 .env のタグの php8.2 を php8.3 に書き換えて
docker compose pull ec-cube && docker compose up -d		 約 20 秒
戻すのも同じ
EC-CUBE
4.3.1 → 4.3.2 など		 bin/upgrade.sh ~4.3.0 --prod 数分
失敗したら何も変えずに止まる
eccube-docker
v1.0.18 → v1.0.19 など		 bin/self-update.sh 1 分
差分を git で見てから commit
PHP だけ変えても EC-CUBE はそのまま PHP はイメージの中に、EC-CUBE と vendor はボリュームの中にあります。だからイメージを差し替えても入れ替わるのは PHP だけで、店のデータにも EC-CUBE の版にも触りません（作り直されるのはアプリのコンテナ 1 つ、約 20 秒）。合わない組み合わせのタグは存在しないので、壊れる前に pull が失敗します。選べる PHP は下の表のとおりです。

こんなところで止まっていませんか

左は実際によく聞く声、右はこの環境がどう片付けるか。ひとつでも当たれば、続きを読む価値があります。

店の担当者 / 引き継いだ人

「脆弱性の案内が来たけど、上げるのが怖くてそのまま。PHP も古いと言われた」 制作会社に頼むと数十万で数週間。自分でやると壊れそうで、戻し方も分からない。

その日に当てる。上げる前に止まる

バックアップを取り、新しい EC-CUBE でプラグインが動くかをお店に触る前に確かめ、ダメなら何も変えずに止まります。スキーマの差分に「列の削除」が混じっていれば、それも止まる。

bin/upgrade.sh ~4.3.2 --prod

初めて自分で公開する人

「サーバーは借りた。でもドメインと SSL の設定で止まっている。ポートを開けるのも怖い」 A レコード、証明書の更新、ファイアウォール。どれか 1 つ間違えると、サイトが出ないか、危ない状態で出る。

ドメインは Cloudflare Tunnel で。ポートを 1 つも開けない

Cloudflare の画面でトンネルを作り、公開ホスト名に shop.example.com → http://nginx:80 と書く。あとは発行されたトークンを .env に 1 行。サーバー側はポートを開けず、A レコードも証明書も触らない（HTTPS は Cloudflare が終端し、更新も向こうがやる）。既定の公開方式なので、追加の設定はこれだけです。

COMPOSE_PROFILES=tunnel
TUNNEL_TOKEN=eyJhIjoi...   # Cloudflare Zero Trust で発行

引き継いだ人

「前の会社が作ったサイト。直したのに反映されない。何がどこにあるか分からない」 キャッシュを消しても変わらない。エラーも出ない。触るのが怖い。

困ったら 1 コマンド。日本語で理由が出る

本番モードの EC-CUBE は、コードを直しても例外も 500 も出さずに古いまま動き続けます。doctor が残骸の掃除・無効プラグインの検出・キャッシュの組み立て直し・疎通確認までやり、何が悪いかを出します。

EC-CUBE とあなたのコードは置き場が分かれています。どこを直せばいいかで迷わない。

bin/plugin.sh doctor

レンタルサーバーから出たい人

「共用サーバーで始めたけど、もう上げられない。VPS に移したい。でも画像と DB とテンプレが散らばっている」 移転の手順を検索すると、人によって言うことが違う。

引っ越しは 3 手順

DB・画像・管理画面が書いたファイル・設定の 4 点セットを 1 コマンドで退避。新しいサーバーでは clone → init → restore。同じ手順がどの VPS でも通ります。

bin/backup.sh
# 新しいサーバーで
bin/init.sh && bin/restore.sh backups/<日時>

制作会社 / フリーランス

「案件ごとにサーバーの手順が違う。前と同じにならない。保守が赤字」 本番の反映で毎回ひやひやする。メンテナンス表示を出し忘れる。

直す場所と動かす場所を分け、反映を 1 コマンドに

退避 → メンテナンス表示 → 取り込み → DB 更新 → キャッシュ → 確認 → 解除。失敗したらメンテナンス表示のまま止まり、壊れた画面をお客さんに出しません。どの案件でも同じ手順。

bin/deploy.sh --remote=shop:/srv/myshop

プラグイン開発者

「本番と同じ環境で試したい。テンプレの上書きと更新で毎回悩む」 写しを置いたら、プラグインを更新しても古いほうが勝ち続けた。

入れる・直す・差分を見る、を揃えてある

private リポジトリから clone して install → enable まで 1 コマンド。テンプレは app/template/plugin/ に写して直し、プラグインを更新したら「自分が変えた／上流が変わった／衝突」を分けて出します。

bin/plugin.sh add git@github.com:you/MyPlugin.git
bin/plugin.sh template add MyPlugin admin/config.twig

毎日はこれだけ

直す場所（手元）と動かす場所（サーバー）を分ける。この環境の全部です。

1

手元で直す

bin/init.sh                # 初回だけ。終わると URL とログイン情報が表示される
2

控えを送る

git add -A && git commit -m "何を直したか" && git push
3

サーバーに反映する

bin/deploy.sh --remote=shop:/srv/myshop

手元から送るので、サーバーに git も GitHub の鍵も要りません（最初の 1 回は bin/bootstrap-server.sh が Docker まで入れる）。数分かかります。終わったらお店を開いて目で確かめる。PHP やミドルウェアのセキュリティパッチも、このときに入ります。

本番には main の先頭と同じものしか送れません。出る前に「何が出るか」を見せ、プロジェクト名を打つまで何も変えない。見るだけなら --check。

本番には、レビュー済みの main しか出ない

エンジニアが直し、担当者が承認して、本番へ出す。「エンジニアが勝手に出す」と「担当者がうっかり出す」を、別々の壁で止めます。どれか 1 枚が無くても残りは効く。

①

GitHub — 承認が無いと main に入らない

bin/setup.sh protect

PR 必須、担当者（CODEOWNERS）の承認必須、force push と削除の禁止。管理者も例外なし。非公開リポジトリは GitHub の有料プランが要ります（無ければ②③だけで運用）。

②

手元 — main の先頭と同じものしか送れない

bin/deploy.sh --remote=shop:/srv/myshop
  ✗ いまのブランチは feature です。出せるのは main だけ

別のブランチ、コミットしていない変更、push していないコミット。どれか 1 つでも本番へは送らない。何もしなくて効きます。

③

サーバー — 見せて、打たせて、記録する

  コード: 3f2a1c0 → 9b7e4d2（3 コミット）
  ⚠ migration が含まれます
  続けるなら、プロジェクト名 myshop を入力:

y では通しません。指が覚えて通してしまわないように、プロジェクト名を打つ。誰が・いつ・何を出したかは var/deploy.log に残る。

正直に 本番の SSH を持つ人は②③を素通りできます。壁は「うっかり」を止めるもので「故意」は止められない。だから本番の SSH はエンジニアに渡さない、と決めてください。詳しくは 本番デプロイ。

アクセスが増えたら、測ってから強くする

どこが先に詰まるかは、店のプラグインとデータの量で変わります。最初に測り、詰まった場所に合う手を、安くて効く順に打ちます。

先に詰まったもの打つ手
画像・CSS・JS の数① CDN（トンネルで公開していれば、もう効いている）
PHP の CPU② Redis → ③ php-fpm の枠 → ④ アプリのホストを並べる
DB の CPU⑤ 遅い SQL を直す → ② Redis → DB を大きくする
特定のページだけそのページで動くプラグインを疑う（外した検証環境で同じ試験を流して比べる）
0

測る

bin/loadtest.sh stress --rate=100

「毎秒何 PV」で流し、段ごとに応答時間と失敗を出す。手元ならコンテナの CPU と php-fpm の上限も。月間 PV から山の PV/秒を出す式は 負荷試験 に。本番には流さない（手元以外はホスト名を打たないと流れない）。

①

CDN — 静的ファイルを中継点に

# caddy で直接公開しているなら、トンネルへ
bin/setup.sh tunnel
# 確かめる（2 回目で HIT）
curl -sI https://店/…/style.css \
  | grep -i cf-cache-status

Cloudflare Tunnel で公開していれば設定は要りません。商品画像は 30 日、名前の変わらない CSS・JS は 5 分（管理画面で直した CSS がすぐ出るように）。Cloudflare の画面では Browser Cache TTL を「Respect Existing Headers」に。「Cache Everything」にはしない（ほかの人のカートが入ったページを配ってしまう）。

②

Redis — 同じ計算をしない

# .env
COMPOSE_PROFILES=tunnel,redis
# 反映
bin/deploy.sh

キャッシュとセッションを Redis へ。DB への同じ問い合わせと PHP の計算が減ります。切り替えた瞬間に全員ログアウトになり、カートも空になるので、お客さんの少ない時間に。

③

php-fpm の枠を広げる

# .env（既定 20。1 本 80MB ほど）
PHP_FPM_MAX_CHILDREN=40
# 反映
bin/deploy.sh

CPU に余裕があるのに、負荷試験で「php-fpm の上限に達した」と出るときに効きます。CPU が張り付いているなら、サーバーを大きくするか ④ へ。

④

アプリのホストを並べる

# 各ホストで（DB・Redis・画像は外へ）
docker compose \
  -f compose.app.yaml up -d
# 前に LB を置く

DB と Redis はマネージドへ、画像は NFS / EFS へ出し、アプリだけを並べます。セッションは Redis で共有なので、同じ人を同じホストへ寄せる設定は要りません。全ホストの php-fpm の枠の合計が DB の接続数の上限（既定 200）を超えると落ちるので、合わせて上げます。

⑤

DB が詰まったら

# 動いている DB にその場で（MariaDB）
SET GLOBAL slow_query_log = 1;
# 設定ファイルは再起動まで効かない

まず遅い SQL を探す（プラグインの 1 本が原因のことが多い）。次に ② の Redis。それでも足りなければ、マネージド DB の上の型へ上げます。

入れていないもの

  • DB の読み取りを複製へ振り分ける: EC-CUBE がリクエストのたびにトランザクションを始めるので、設定を足しても複製は一度も使われません。
  • ページ（HTML）のキャッシュ: 商品一覧・詳細には人ごとのトークンが、ヘッダーには人ごとのカートとログインの欄があります。そのまま配ると、ほかの人のカートが見え、「カートに入れる」が失敗します。
正直に 何 PV まで耐えるかは、まだ本番と同じ形の環境で測っていません。手元の Mac（8 CPU、サンプルデータ）では 20 PV/秒までが安全で、先に詰まったのは PHP の CPU でした。設定の詳しい手順は 大規模アクセス。

向いている人・向いていない人

正直に書きます。合わない人が使うと、お互いに時間を失うので。

向いている

  • Docker が動く VPS かクラウドで EC-CUBE 4 を運用する（これから移る人も）
  • ドメインと HTTPS を Cloudflare Tunnel で済ませたい（ポートを開けず、証明書の更新から解放される）
  • メールサーバーや DB の設定を手で書きたくない（bin/setup.sh mail / db が質問に答えるだけで、先に試してから書く）
  • 制作会社・フリーランスで、複数の案件を同じ手順で回したい
  • 複数人で運用する（エンジニアが直して担当者が出す。本番には承認済みの main しか出ない）
  • 前任者のいないサイトを引き継いで、まず状況を把握したい
  • プラグインやテーマを作っていて、本番と同じ環境で試したい
  • ターミナルでコマンドを打つことに抵抗がない（Windows は WSL2 の中で）
  • AI に運用を手伝わせたい（Claude Code / Codex 向けの指示書 AGENTS.md が入っていて、やることと絶対にやらないことが書いてある）
  • DB は MariaDB 派でも PostgreSQL 派でも（.env に 1 行。どちらも同梱、外部のマネージド DB も可）

向いていない

  • 共用レンタルサーバー（Docker が動かない）。移るときに戻ってきてください
  • 管理画面だけで全部済ませたい（テンプレートは git で持つ設計です）
  • Windows でコマンドを触りたくない
ひとこと 初回は Redis も非同期メールも無効で、必要になったら .env に 1 行足す設計です。最初から全部入りではありません。

何がしたいですか？

毎日の手順は はじめての人のための手引き。
A

新規作成

パソコンで動かしてから、サーバーに出します。サーバーには何も入れに行きません。全部パソコンから打ちます。

時間: パソコンで動くまで 5 分、公開まで 30 分ほど。

git clone はしません。clone だと送り先が配布元のままで、あなたのコードを保存する場所がありません。中身だけもらって、自分専用の非公開リポジトリにします。

  1. パソコン中身をもらう

    curl -fsSL https://github.com/kurozumi/eccube-docker/releases/latest/download/eccube-docker.tar.gz | tar -xz
mv eccube-docker-* myshop && cd myshop

  2. パソコン自分の非公開リポジトリにする

    git init -b main && git add -A && git commit -m "eccube-docker から開始"
gh repo create myshop --private --source=. --push

  3. パソコン動かしてみる

    bin/init.sh --image=ghcr.io/kurozumi/eccube-docker/ec-cube:4.3-php8.3

    数十秒で終わり、URL（http://localhost:8080/）と管理画面のログイン情報が出ます。4.3 が EC-CUBE の版、php8.3 が PHP の版です。

  4. サーバーサーバーを整える（パソコンから打つ）

    bin/bootstrap-server.sh user@サーバー /srv/myshop

    Docker を入れ、お店のファイルを送ります。サーバーは SSH で入れるようにしておくだけ。

  5. サーバーメールと公開の設定（パソコンから打つ）

    bin/setup.sh mail   --remote=user@サーバー:/srv/myshop
bin/setup.sh tunnel --remote=user@サーバー:/srv/myshop

    質問に答えるだけ。メールは 1 通試してから、公開は Cloudflare につながるか試してから書きます。

  6. サーバー公開して、毎日のバックアップを入れる

    bin/publish.sh      --remote=user@サーバー:/srv/myshop
bin/setup.sh backup --remote=user@サーバー:/srv/myshop

  7. ブラウザお店を開いて確かめる

    これ以降、直したものを出すのは bin/deploy.sh --remote=user@サーバー:/srv/myshop だけです。詳しくは 導入手順。

B

EC-CUBE のバージョンアップ

例: EC-CUBE 4.3.1 → 4.3.2。パソコンで試してから、サーバーで上げます。

時間: お店が止まるのは数分。

そのまま残るもの: 受注・会員・商品・画像、あなたが直したテンプレートや CSS、プラグイン。
失敗したら: 何も変えずに止まります。そのままのお店が動き続けます。

  1. どの番号が変わるかを見る

    3 つ目だけ（4.3.1 → 4.3.2）パッチ。このまま次へ。
    2 つ目（4.3 → 4.4）プラグインの作り直しが要ります。ひとりで進めず、制作者に相談してください（バージョンアップ）。

  2. パソコン先に環境を新しくする

    下の C を済ませます。古い道具で新しい EC-CUBE を扱わないためです。

  3. パソコンパソコンで上げて、試す

    bin/upgrade.sh ~4.3.0

    ~4.3.0 は「4.3 の中で一番新しい版」。確認が出たら y。終わったら http://localhost:8080/ で、トップ・商品・カート・管理画面を開いてみます。

  4. サーバーお客さんに告知してから、サーバーで上げる

    ssh user@サーバー
cd /srv/myshop
bin/upgrade.sh ~4.3.0 --prod

    --prod を必ず付けます。自動でバックアップを取り、新しい EC-CUBE でプラグインが動くかを、お店に触る前に確かめます。

  5. ブラウザ目で確かめる

    トップ・商品詳細・カートに入れる・管理画面のログイン・受注一覧。おかしければ bin/plugin.sh doctor。

C

環境のアップデート

例: eccube-docker v1.0.18 → v1.0.19。パソコンで取り込み、いつもの deploy でサーバーへ。サーバーで直接は取り込みません。

時間: 5 分ほど。お店はほとんど止まりません。

触らないもの: EC-CUBE の版、お店のデータ、あなたが直したもの、.env。
新しくなるもの: bin/ のコマンド、サーバーの組み立て、文書。

  1. パソコン何が変わるかを見る

    bin/self-update.sh --check

    まだ何も書き換えません。リリースノートの「まずやること」も読みます。版によっては、ひと手間あります。

  2. パソコン取り込む

    bin/self-update.sh

    配布元が変えたファイルだけを差し替えます。あなたが手を入れたファイルとぶつかるときは、上書きせずに止まって知らせます。

  3. パソコン控えを送る

    git add -A && git commit -m "eccube-docker v1.0.19" && git push

  4. サーバーいつもどおり反映する（パソコンから打つ）

    bin/deploy.sh --remote=user@サーバー:/srv/myshop

  5. ブラウザお店を開いて確かめる

対応する EC-CUBE

配布イメージを使うと、手元でビルドせずに数十秒で立ち上がります（bin/init.sh --image=… か .env の ECCUBE_IMAGE）。PHP はタグで選びます: 4.3-php8.3 のように書くとその PHP、-php を省くと系列の既定。

系列イメージ（本番はこれ）選べる PHP備考
4.3ghcr.io/kurozumi/eccube-docker/ec-cube:4.38.1† / 8.2 / 8.3推奨
4.2ghcr.io/kurozumi/eccube-docker/ec-cube:4.28.1† / 8.2
4.4ghcr.io/kurozumi/eccube-docker/ec-cube:4.48.2 / 8.3 / 8.4 / 8.5上流の開発ブランチから焼いている。同じものを立てたいなら日付タグで固定

公式の PHP イメージが作り直されたら、翌朝その組だけ焼き直します（月曜は全部）。PHP のセキュリティパッチは公開の翌日に入り、OS のパッチも遅くとも 1 週間で入ります。受け取るのは bin/deploy.sh（nginx・Redis・DB などのミドルウェアも一緒に引き直す）。ミドルウェアの脆弱性・保守期限・Docker の設定も毎日点検しています。 †PHP 8.1 は 2025 年 12 月で終了しています。OS のパッチは入りますが PHP 自体の修正はもう出ないので、8.1 でしか動かないプラグインが無ければ 8.2 以上を。太字は -php 無しの既定。PHP を選ぶなら 4.4-php8.5 のように書く。同じものを何度も立てたい人は日付タグ 4.3-20260907、リリース時点なら 4.3-__TAG__。

DB は MariaDB / MySQL（既定）か PostgreSQL。版は .env の MARIADB_VERSION / PG_VERSION。.env の DB_ENGINE で選び、バックアップも引っ越しも同じコマンドで通ります。手元の DB でも、クラウドのマネージド DB でも。

はじめての人のための手引き

登場するものは 5 つ、毎日やることは 3 つ、困ったときは 1 コマンド。理由は書きません。

導入手順

取得から公開まで。.env の中身、公開方式、プラグインの扱い、デザインを直す場所。

バージョンアップ

運用中の店を上げる手順と切り戻し。マイナーをまたぐときに黙って壊れる 3 つの型。

データを失わないために

down と down -v の違い、消えるコマンド、消したときの復旧。

本番デプロイ

誰が・何を・どうやって本番へ出すか。3 枚の壁、--check、記録、緊急時、誰に何を渡すか。

バックアップ / 復元

5 点セット、送り先、暗号化、引っ越し。bin/setup.sh backup が毎日の cron まで入れる。

大規模アクセス

CDN、Redis、アプリを並べる、DB を外に出す。打ち手を安くて効く順に。

負荷試験

何 PV/秒まで耐えるか・どこが先に詰まるかを測る。目標の決め方と読み方。

困ったこと、こう動いてほしいを聞かせてください
