大規模アクセス

どの規模まで受け止められるか、どこが先に詰まるかを測り、詰まった場所に合う手を、安くて効く順に打ちます。

アクセスを受け止める仕組み

お客さんの 1 回のアクセスが通る順に、それぞれの場所で効いている仕組みです。印の付いていないものは、何もしなくても最初から効いています。

  1. 1CDNCloudflare
    • 画像・CSS・JS を、お客さんに近い中継点から配る。Cloudflare Tunnel で公開していれば、設定なしで効きます。商品画像は 30 日、CSS・JS は 5 分（管理画面で直した CSS がすぐ出るように。Cloudflare の画面で Browser Cache TTL を「Respect Existing Headers」にしておく。既定の 4 時間のままだと、ブラウザが古い CSS を持ち続けます）。
    • サーバーの 80 / 443 を外に開けずに済みます（入口はトンネルだけ）。
  2. 2nginx入口
    • 静的ファイルは PHP を通さずに返す（圧縮とキャッシュの指示つき）。
    • ログインとパスワード再発行に回数制限（1 つの IP から 1 分に 10 回）。総当たりで PHP が埋まりません。
    • PHP を複数並べたとき（--scale）は、その間で振り分けます。
  3. 3PHPphp-fpm
    • OPcache を本番向けに（ファイルの更新を毎回確かめない）。コンパイル済みのコードをメモリから使います。
    • 同時に処理する数（php-fpm の枠）は .env で変えられる（既定 20）。数字 1 つ
    • メールは非同期で送れる（Messenger）。worker が動いていれば、メールサーバーが止まっていても注文の確定は待たされません（入れられなかったときは、これまでどおりその場で送ります）。スイッチ 1 つ
  4. 4Redisキャッシュ・ログイン
    • 同じ計算と DB への同じ問い合わせを、キャッシュから返す。スイッチ 1 つ
    • ログインの状態とカートの目印を Redis に置く（キャッシュとは別の Redis。あふれても消えない設定。カートの中身は DB）。サーバーを何台に増やしても、同じ人が同じサーバーに当たる必要がありません。上と同じスイッチ
  5. 5DB・画像MariaDB / PostgreSQL
    • DB の設定は EC-CUBE 向けに調整済み（メモリの使い方、接続数）。マネージド DB へは bin/setup.sh db で移せます。スイッチ 1 つ
    • 商品画像はアプリと別の置き場にあり、NFS / EFS へ差し替えれば全サーバーで共有できます。
  6. +サーバーを並べるロードバランサー
    • アプリだけを動かす構成（compose.app.yaml）を何台でも並べ、前にロードバランサーを置けます。DB・Redis・画像は共有。台数を増やすとき
    • 反映は 1 台ずつ（止めずに更新）、EC-CUBE を上げるときだけ全台を止めます。手順は下の「複数のサーバーに分ける」。
強くする前に測る どこが先に詰まるかは店ごとに違うので、bin/loadtest.sh（k6）で「毎秒何 PV」を流して確かめてから、詰まった場所の仕組みを足します。注文は流しません。流す先は、本番と切り離した検証環境にしてください（手元以外へはホスト名を打たないと流れないのは、向き先の取り違えを防ぐためで、本番を見分けているわけではありません）。下の表が、詰まった場所ごとの打つ手です。

どの規模まで受け止められるか

1 日の PV を 1 秒あたりに直し、混む時間（平均のおよそ 4 倍）でどれだけ来るかを見ます。サーバー 1 台で受けられる量は推定です（下の「正直に」）。

1 日の PV混む時間の毎秒 PV構成の目安この環境で
10 万約 5サーバー 1 台余裕
100 万約 50強めの 1 台 + Redis + CDN。足りなければアプリを 2 台に範囲内
1,000 万約 500アプリのサーバー 10〜20 台 + 大きなマネージド DB。ページを使い回せるようにテーマを作り直す挑戦できる上限
1 億約 5,000作りそのものを変える（下）範囲外

数え方

  • 平均の毎秒 PV = 1 日の PV ÷ 86,400 秒（1 億なら約 1,200）。
  • 混む時間は平均のおよそ 4 倍。セールやテレビの直後は、さらに何倍にもなります。
  • PV は「ページの表示」の数です。画像・CSS・JS は CDN が受けるので、ここには数えていません。

1 億 PV で壁になるもの

  • ページを使い回せない: 商品ページに人ごとのカート・ログイン・トークンが入るので、毎回 PHP で作ることになります。
  • DB が 1 台: 1 ページで何十回も問い合わせるので、毎秒数十万回になり、いちばん大きい DB でも足りません。EC-CUBE は読み取り用の複製を使えません。
  • セールの殺到: 強くするだけでは受け切れず、入場待ちの列（Cloudflare Waiting Room など）で絞ることになります。

1 億 PV を本当にやるなら、画面を作る部分と注文を受ける部分を分け（ヘッドレス）、商品ページは CDN から配って人ごとの部分だけを後から取りに行き、検索は専用の検索エンジンへ、DB はデータの種類ごとに分けます。日本でも最大級の通販サイトの規模で、EC-CUBE を土台にするかどうかから考え直す話になります。

正直に 実際に測れたのは、手元の Mac（8 CPU、サンプルデータ）で毎秒 20 PV までです。本番の大きなサーバー 1 台で毎秒 30〜50 PV と見込んでいますが、本番と同じ形の環境ではまだ測っていません。プラグインとデータの量で大きく変わるので、自分の店の数字は、検証環境で bin/loadtest.sh を流して確かめてください。

よくある疑問

DB も複数台に分けるの？

  • 分けません。1 台のまま大きくします。増やすのはアプリのサーバーだけで、全台が同じ DB を見ます。
  • 読み取り用の複製（リードレプリカ）は、EC-CUBE がリクエストのたびに書き込み用の接続を使うので効きません。データを複数の DB に分けるのも、EC-CUBE の作りでは現実的ではありません。
  • DB が詰まったら、遅い SQL を直す → Redis で問い合わせを減らす → DB を大きくする、の順です。

1 台で動いている店から、途中で分けられる？

  • 分けられます。部品を 1 つずつ、別の日に外へ出します。
  • DB（bin/setup.sh db）→ Redis（.env を書き換える）→ 商品画像（NFS / EFS）→ アプリのサーバーを足して LB を置く、の順。
  • アプリを増やすときは、先に今のサーバーの前に LB を置き、そこへ 2 台目を足すので、止めずにできます。

お店が止まる時間は？

  • 毎日の反映・PHP の更新: 複数台なら 0（1 台ずつ LB から外して反映）。
  • EC-CUBE 本体の更新: 数分。古い版と新しい版を同時に動かせないので、全台を止めます。
  • DB を外へ移す（1 回だけ）: 数分〜数十分（データの量しだい）。Redis を入れるとき: bin/deploy.sh のメンテナンス表示の間（1 分ほど）止まり、全員ログアウトになります。

AWS を使えば考えなくてよくなる？

  • 減るのは「機械の面倒を見る手間」で、「どう分けるか」は残ります。
  • 任せられる: DB のバックアップと故障時の切り替え（RDS）、Redis（ElastiCache）、画像の共有（EFS）、LB と証明書（ALB）。
  • 残る: DB は 1 台のまま。ログイン・画像・管理画面が書くファイルを共有する設計。EC-CUBE の更新は全台を止める。台数の自動の増減は、この環境の docker compose のままではできません（ECS などへの載せ替えが要る）。料金も上がります。

アクセスが増えたら、測ってから強くする

どこが先に詰まるかは、店のプラグインとデータの量で変わります。最初に測り、詰まった場所に合う手を、安くて効く順に打ちます。

先に詰まったもの打つ手
画像・CSS・JS の数① CDN（トンネルで公開していれば、もう効いている）
PHP の CPU② Redis → ③ php-fpm の枠 → ④ アプリのホストを並べる
DB の CPU⑤ 遅い SQL を直す → ② Redis → DB を大きくする
特定のページだけそのページで動くプラグインを疑う（外した検証環境で同じ試験を流して比べる）
0

測る

bin/loadtest.sh stress --rate=100

「毎秒何 PV」で流し、段ごとに応答時間と失敗を出す。手元ならコンテナの CPU と php-fpm の上限も。月間 PV から山の PV/秒を出す式は 負荷試験 に。本番には流さない（手元以外はホスト名を打たないと流れない）。

①

CDN — 静的ファイルを中継点に

# caddy で直接公開しているなら、トンネルへ
bin/setup.sh tunnel
# 確かめる（2 回目で HIT）
curl -sI https://店/…/style.css \
  | grep -i cf-cache-status

Cloudflare Tunnel で公開していれば設定は要りません。商品画像は 30 日、名前の変わらない CSS・JS は 5 分（管理画面で直した CSS がすぐ出るように）。Cloudflare の画面では Browser Cache TTL を「Respect Existing Headers」に。「Cache Everything」にはしない（ほかの人のカートが入ったページを配ってしまう）。

②

Redis — 同じ計算をしない

# .env
COMPOSE_PROFILES=tunnel,redis
# 反映
bin/deploy.sh

キャッシュとセッションを Redis へ。DB への同じ問い合わせと PHP の計算が減ります。切り替えた瞬間に全員ログアウトになり、カートも空になるので、お客さんの少ない時間に。

③

php-fpm の枠を広げる

# .env（既定 20。1 本 80MB ほど）
PHP_FPM_MAX_CHILDREN=40
# 反映
bin/deploy.sh

CPU に余裕があるのに、負荷試験で「php-fpm の上限に達した」と出るときに効きます。CPU が張り付いているなら、サーバーを大きくするか ④ へ。

④

アプリのホストを並べる

# 各ホストで（DB・Redis・画像は外へ）
docker compose \
  -f compose.app.yaml up -d
# 前に LB を置く

DB と Redis はマネージドへ、画像は NFS / EFS へ出し、アプリだけを並べます。セッションは Redis で共有なので、同じ人を同じホストへ寄せる設定は要りません。全ホストの php-fpm の枠の合計が DB の接続数の上限（既定 200）を超えると落ちるので、合わせて上げます。手順は下の「複数のサーバーに分ける」。

⑤

DB が詰まったら

# 動いている DB にその場で（MariaDB）
SET GLOBAL slow_query_log = 1;
# 設定ファイルは再起動まで効かない

まず遅い SQL を探す（プラグインの 1 本が原因のことが多い）。次に ② の Redis。それでも足りなければ、マネージド DB の上の型へ上げます。

入れていないもの

  • DB の読み取りを複製へ振り分ける: EC-CUBE がリクエストのたびにトランザクションを始めるので、設定を足しても複製は一度も使われません。
  • ページ（HTML）のキャッシュ: 商品一覧・詳細には人ごとのトークンが、ヘッダーには人ごとのカートとログインの欄があります。そのまま配ると、ほかの人のカートが見え、「カートに入れる」が失敗します。
正直に 何 PV まで耐えるかは、まだ本番と同じ形の環境で測っていません。手元の Mac（8 CPU、サンプルデータ）では 20 PV/秒までが安全で、先に詰まったのは PHP の CPU でした。設定の詳しい手順は 大規模アクセス。

複数のサーバーに分ける

1 台で足りるうちは 1 台で。更新もバックアップも管理画面も、台数ぶん手間が増えます。上の ①〜③ を打っても PHP が詰まるときに使います。

置くものどこに
DBマネージド DB か別のサーバー（全台が同じものを見る）
Redis 2 つキャッシュ用とログイン用を別々に
商品画像NFS / EFS（サーバーごとに別の画像にならないように）
アプリ各サーバーで compose.app.yaml。1 台だけが DB の構造を変える役（init 役）
前の振り分け（LB）自前の nginx・Cloudflare Load Balancing・AWS ALB。HTTPS はここで終える
1

まず 1 台で店を作る

bin/init.sh
bin/publish.sh

アプリ専用のサーバーの上では、新しく店を作れません。いつもどおり 1 台で本番まで持っていきます。

2

DB・Redis・画像を外へ

bin/setup.sh db
# .env で redis を有効に
# URL を外の Redis へ

DB は写す先に店があれば止まり、写している間はメンテナンス表示です。Redis を切り替えた瞬間に全員ログアウトになるので、時間を選びます。

3

アプリのサーバーを用意する

# .env は 1 台目を写してから直す
COMPOSE_FILE=compose.app.yaml
HTTP_BIND=10.0.0.11
ECCUBE_IMAGE=…:4.3-php8.3-20261123

HTTP_BIND はそのサーバーのプライベート IP（必須。LB 以外から届かないように）。ECCUBE_AUTH_MAGIC は全台同じに（違うと、そのサーバーでは誰もログインできません）。イメージは日付タグで全台を揃えます。init 役だけ ECCUBE_SKIP_DB_INIT=0。

4

LB を前に置く

# 自前の nginx なら
docker/nginx/lb.conf.example

各サーバーの :8080 へ振ります。TRUSTED_PROXIES は書きません（書くと HTTPS と判定されず、Cookie に Secure が付きません）。

毎日の反映は 1 台ずつ

  • LB から外す → bin/deploy.sh → 開くのを確かめて戻す、を 1 台ずつ。
  • DB の構造が変わるときは init 役から。古いコードでも壊れない変え方にします。
  • エンティティやプラグインが変わるときは、1 台ずつにせず、EC-CUBE を上げるときと同じく全台を止め、init 役 → 残りの順に bin/deploy.sh（共有のキャッシュを古いサーバーが読んで落ちるため）。
  • バックアップは init 役の 1 台だけで取り、外へ送ります。

EC-CUBE を上げるときは全台を止める

  • LB をメンテナンス表示にし、init 役以外を止めます。
  • init 役で bin/upgrade.sh（失敗したら自動で元の版に戻ります）。
  • 残りのサーバーも同じタグで bin/upgrade.sh。DB には触りません。
管理画面が書くファイル ページ管理・ブロック管理・CSS 管理が書くファイルは、書いたサーバーにしかありません。共有ストレージに置くか、管理画面を 1 台に固定します。詳しい手順は 大規模アクセス「複数ホスト + ロードバランサ」。
